## 资源与持久化存储

| 数据 | PVC 容量 | 节点 | 本地目录 |
| --- | --- | --- | --- |
| Prometheus TSDB | 5 GiB | `rke2-worker-1` | `/var/lib/monitoring/prometheus` |
| Grafana 数据库 | 1 GiB | `rke2-worker-2` | `/var/lib/monitoring/grafana` |
| Alertmanager 状态 | 1 GiB | `rke2-worker-3` | `/var/lib/monitoring/alertmanager` |

三个 PV 使用 `monitoring-local` StorageClass、`ReadWriteOnce`、`Retain` 回收策略和节点亲和性。Grafana 的 PVC 名称为 `grafana-data`，Prometheus 和 Alertmanager 的 PVC 由对应 StatefulSet 创建。

Prometheus 保留最近 3 天的数据，数据块保留容量设置为 `3GB`；WAL、head block 和其他临时数据还会占用磁盘。虚拟机系统磁盘容量为 20 GiB，必须同时检查根文件系统的可用空间。Local PV 的声明容量用于 Kubernetes 资源绑定，实际数据与根文件系统共享容量。

Prometheus 请求 200m CPU、512 MiB 内存，限制为 1 CPU、1536 MiB 内存。Grafana 主容器请求 100m CPU、128 MiB 内存，限制为 500m CPU、512 MiB 内存。Alertmanager 请求 50m CPU、64 MiB 内存，限制为 300m CPU、256 MiB 内存。Operator、exporter、sidecar 的 requests 和 limits 见随附 `values.yaml`。

四台虚拟机位于同一宿主机。Local PV 数据随对应虚拟机磁盘保存；节点故障期间，对应有状态组件需要等待该节点恢复。etcd 快照保存 Kubernetes 对象，业务 PV 数据需要单独备份。

## RKE2 指标接口

控制平面附加配置保存到 `/etc/rancher/rke2/config.yaml.d/monitoring.yaml`：

```yaml
etcd-expose-metrics: true
kube-controller-manager-arg:
  - bind-address=0.0.0.0
kube-scheduler-arg:
  - bind-address=0.0.0.0
kube-proxy-arg:
  - metrics-bind-address=0.0.0.0:10249
```

三个工作节点的附加配置为：

```yaml
kube-proxy-arg:
  - metrics-bind-address=0.0.0.0:10249
```

| 采集对象 | 接口 | 认证和校验 |
| --- | --- | --- |
| Kubernetes API | `6443/HTTPS` | ServiceAccount token 和集群 CA |
| kubelet 与 cAdvisor | `10250/HTTPS` | ServiceAccount token 和集群 CA |
| controller-manager | `10257/HTTPS` | ServiceAccount token、集群 CA，TLS server name 为 `localhost` |
| scheduler | `10259/HTTPS` | ServiceAccount token、集群 CA，TLS server name 为 `localhost` |
| etcd metrics | `2381/HTTP` | 虚拟机内部网络接口 |
| kube-proxy | `10249/HTTP` | 虚拟机内部网络接口 |
| node-exporter | `9100/HTTP` | 虚拟机内部网络接口 |

RKE2 的 scheduler 和 controller-manager 服务证书包含 `localhost`，由 RKE2 server CA 签发。采集配置使用该 server name 并校验证书。`prepare-host.sh` 安装附加配置、创建数据目录并依次重启四个 RKE2 服务。

## 下载 Helm chart 与离线镜像

本次使用 Helm `v3.19.0`。Helm 配置、缓存和数据目录均放在任务目录下。

控制平面安装的 Helm 位于 `/usr/local/bin/helm`。重新准备安装环境时，将官方 `helm-v3.19.0-linux-amd64.tar.gz` 放入宿主机材料目录，并执行随附的 `install-tools.sh`。该脚本将 Helm、chart、存储清单和配置文件传入控制平面的 `/home/ubuntu/monitoring`。

```bash
helm pull oci://ghcr.io/prometheus-community/charts/kube-prometheus-stack \
  --version 92.14.0 --destination work/monitoring
```

chart OCI digest：

```text
sha256:a7cb3c6e55acc9cd7cc918fe1e4f62f6da57102255939577a051188e586340c0
```

在可访问镜像仓库且安装 Docker 的机器执行：

```bash
bash work/monitoring/download-images.sh
```

脚本按 `images.txt` 下载 `linux/amd64` 镜像，导出 `monitoring-images.tar.gz` 并生成 `monitoring-images.sha256`。镜像清单包括 Operator、config-reloader、Prometheus、Grafana、Grafana sidecar、Alertmanager、node-exporter、kube-state-metrics、webhook 证书生成组件及 Helm 测试镜像。

本次镜像包大小为 742,741,345 字节，SHA256 为：

```text
3d301fa3af710ab02d5005d7ab1a5dfc02a148a83bf0729f7461ab4f705451ca
```

通过跳板机将离线镜像包、校验文件和 `import-images.sh` 复制到宿主机 `/var/lib/rke2-lab/monitoring`，然后执行：

```bash
cd /var/lib/rke2-lab/monitoring
sha256sum -c monitoring-images.sha256
bash import-images.sh
```

`import-images.sh` 校验镜像包，将其分发到四台虚拟机，并使用各节点的 containerd `k8s.io` namespace 导入。成功后删除各虚拟机中的临时传输包，宿主机保留原始镜像材料。

## 创建存储与 Grafana 登录凭证

在宿主机执行数据目录和 RKE2 指标接口准备脚本：

```bash
cd /var/lib/rke2-lab/monitoring
bash prepare-host.sh
```

以下 `kubectl`、`helm` 命令均要求使用本集群的管理员 kubeconfig。控制平面的原始 kubeconfig 位于 `/etc/rancher/rke2/rke2.yaml`，`kubectl` 位于 `/var/lib/rancher/rke2/bin`。

在控制平面执行：

```bash
sudo -i
export PATH=/var/lib/rancher/rke2/bin:$PATH
export KUBECONFIG=/etc/rancher/rke2/rke2.yaml
cd /home/ubuntu/monitoring
```

```bash
kubectl apply -f storage.yaml
```

为首次部署生成随机管理员密码：

```bash
umask 077
printf 'admin-user=admin\nadmin-password=%s\n' "$(openssl rand -hex 24)" \
  > grafana-admin.env
kubectl -n monitoring create secret generic grafana-admin \
  --from-env-file=grafana-admin.env
```

`values.yaml` 通过 `grafana.admin.existingSecret: grafana-admin` 引用凭证。现有环境保留已创建的 Secret；随附安装配置包不包含密码文件或管理员 kubeconfig。

## 安装监控组件

```bash
helm upgrade --install monitoring kube-prometheus-stack-92.14.0.tgz \
  --namespace monitoring \
  --values values.yaml \
  --wait --timeout 10m --history-max 5
```

检查资源：

```bash
helm status monitoring -n monitoring
kubectl -n monitoring get pods -o wide
kubectl -n monitoring get pvc
kubectl get pv
kubectl -n monitoring get servicemonitors,prometheusrules
```

`values.yaml` 配置了三个 NodePort：Grafana `30300`、Prometheus `30900`、Alertmanager `30903`。这些端口位于虚拟机内部网络，校外通过 SSH 转发访问。

## Grafana 使用方法

登录后打开 Dashboards，查找 Kubernetes 和 Node Exporter 相关仪表盘。根据 Cluster、Namespace、Node、Workload 和 Pod 等筛选条件查看指标。常用内容包括节点 CPU 和内存、磁盘空间、网络吞吐、Pod 重启次数、工作负载副本状态，以及 CPU 和内存 requests 与 limits。

本集群常用的仪表盘名称：

- `Kubernetes / Compute Resources / Cluster`
- `Kubernetes / Compute Resources / Node (Pods)`
- `Kubernetes / Compute Resources / Namespace (Pods)`
- `Kubernetes / Compute Resources / Pod`
- `Node Exporter / Nodes`
- `Kubernetes / Networking / Cluster`
- `Kubernetes / Persistent Volumes`
- `etcd`
- `Prometheus / Overview`
- `Alertmanager / Overview`

Prometheus 数据源由 chart 自动配置。修改显示时间范围后，可以查看对应时间内的历史曲线；指标保留期限由 Prometheus 配置控制。

## Prometheus 查询方法

打开 Query 页面输入 PromQL：

```promql
count(kube_node_info)
```

该查询返回集群节点数量。其他查询示例：

```promql
up
```

```promql
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))
```

```promql
100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
```

```promql
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!="",container!="POD"}[5m]))
```

```promql
sum by (namespace, pod) (container_memory_working_set_bytes{container!="",container!="POD"})
```

```promql
sum by (namespace, pod) (kube_pod_container_status_restarts_total)
```

打开 Status 中的 Targets 检查采集状态和最近一次错误。`up = 1` 表示最近一次采集成功；查询窗口需要包含足够的样本，`rate(...[5m])` 才能形成曲线。

## Alertmanager 使用方法

Prometheus 根据 PrometheusRule 执行告警表达式。条件持续达到规则中的 `for` 时长后，告警从 pending 转为 firing 并交给 Alertmanager。Alertmanager 页面可以查看标签、分组和静默条件。

创建静默时填写精确的标签匹配、开始时间、结束时间和原因。静默只影响通知处理，Prometheus 中的规则仍然执行。chart 的 `Watchdog` 告警持续 firing，用于观察告警链路。
