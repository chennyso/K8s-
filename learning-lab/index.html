2．从容器运行理解 Kubernetes

执行一次容器启动命令，只能描述某个时刻的操作。应用运行期间还需要处理进程退出、节点故障、多个副本、访问入口和版本更新。Kubernetes 保存资源的期望状态，控制器持续检查实际状态，并执行创建、更新等操作。

当前节点使用 containerd 运行容器。Docker 在宿主机承担镜像构建等工作。镜像需要匹配节点的 linux/amd64 架构，并且节点必须能够取得镜像及认证信息。

概念 在当前项目中的例子 作用
镜像 learning/tasks:1.0.1 保存程序、运行环境和依赖
容器 server、writer、inspector 运行具体进程
Pod pod-web 的一个副本 提供共享网络及声明的卷挂载
Deployment pod-web 管理副本和滚动更新
ReplicaSet pod-web 对应的副本集合 维持符合模板的 Pod 数量
Service pod-web 根据标签关联后端并提供稳定访问地址
Namespace pod-lab 给资源提供命名范围
ConfigMap 项目的脚本及网页配置 将配置文件提供给容器
Secret 数据库密码、仓库认证 保存需要限制访问的配置
PVC PostgreSQL 数据卷申请 申请持久化存储

Namespace 的隔离能力需要 RBAC、配额和网络策略共同配置。Secret 的访问权限需要明确控制，Base64 编码能够还原原文。

3．理解创建应用时发生的事情

sequenceDiagram
    participant U as kubectl
    participant A as API Server
    participant E as etcd
    participant C as 控制器
    participant S as Scheduler
    participant K as kubelet
    participant R as containerd
    U->>A: 提交 Deployment
    A->>E: 保存通过校验的资源
    C->>A: 创建 ReplicaSet 和 Pod
    S->>A: 为未调度 Pod 绑定节点
    K->>A: 获取分配到本节点的 Pod
    K->>R: 请求创建容器
    K->>A: 更新运行与就绪状态

控制器通过 API Server 观察资源。scheduler 根据 requests、节点条件和调度约束选择节点；kubelet 请求容器运行环境启动进程。网络插件配置 Pod 网络，存储组件准备声明的卷。Pod 的状态可能依次出现 Pending、初始化、Running 等变化。

Running 表示 Pod 已进入运行阶段，接收业务流量还需要检查 Ready。项目中三个普通容器全部就绪时显示 3/3。查看状态时同时检查 READY、STATUS、RESTARTS 和事件。

4．阅读实际 YAML 文件

解压源码后打开 pod-lab/workload.yaml 和 pod-lab/access.yaml，按照以下关系阅读。下面的代码块用于解释字段，完整可部署配置保存在源码文件中。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: pod-web
  namespace: pod-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: pod-web
  template:
    metadata:
      labels:
        app: pod-web

apiVersion 指定资源 API 组和版本。kind 指定对象类型。metadata.name 和 metadata.namespace 定位对象。spec.replicas 声明数量。selector.matchLabels 必须匹配 Pod 模板标签。template 描述将来创建的 Pod；修改模板通常会触发新的 ReplicaSet 和滚动更新。

Service 的 selector 同样匹配 Pod 标签。port 是 Service 提供的端口，targetPort 指向容器实际监听端口，nodePort 是 NodePort 类型在节点提供的端口。容器的 containerPort 字段描述端口，程序仍然需要实际监听对应地址。

使用集群提供的字段说明查阅配置：

kubectl explain deployment.spec.template.spec
kubectl explain deployment.spec.template.spec.containers.resources
kubectl explain service.spec.ports
kubectl -n pod-lab get deployment pod-web -o yaml
kubectl -n pod-lab get service pod-web -o yaml

输出中 spec 是声明的配置，status 是系统报告的状态。比较两者，可以判断控制器是否已经完成预期操作。

5．部署和访问 Pod 项目

首次搭建按照部署手册准备节点目录与监控依赖，然后进入源码 pod-lab/ 执行 bash deploy.sh。已有环境直接开始下面检查：

kubectl -n pod-lab get deployment,replicaset,pod,service -o wide
kubectl -n pod-lab rollout status deployment/pod-web --timeout=180s
kubectl -n pod-lab get endpointslice -l kubernetes.io/service-name=pod-web
kubectl -n pod-lab port-forward service/pod-web 18084:8080

保持最后一个命令运行，在 Mac 浏览器访问 http://127.0.0.1:18084。网页显示计数器和 Pod 状态。另一个终端可以执行：

curl --fail http://127.0.0.1:18084/status.json

本机请求经过 kubectl 与 API Server 到达选中的 Pod。port-forward 选中的 Pod 被删除后，需要重新建立转发。使用这个入口验证页面可达，集群内部的 Service 转发另外通过客户端 Pod 验证：

kubectl -n pod-lab exec client-allowed -- nslookup pod-web.pod-lab.svc.cluster.local
kubectl -n pod-lab exec client-allowed -- wget -qO- -T 5 http://pod-web:8080/status.json

DNS 返回 Service 地址，Service 的后端由匹配标签及就绪条件的 EndpointSlice 描述。测试多副本时观察实际响应中的 Pod 信息和端点列表；单个长期连接可能持续使用同一个后端。

6．观察容器、进程和日志

POD=$(kubectl -n pod-lab get pod -l app=pod-web -o jsonpath='{.items[0].metadata.name}')
kubectl -n pod-lab describe pod "$POD"
kubectl -n pod-lab logs "$POD" -c writer --tail=20
kubectl -n pod-lab exec "$POD" -c inspector -- ps
kubectl -n pod-lab exec "$POD" -c inspector -- wget -qO- http://127.0.0.1:8080/status.json

server 提供 HTTP 服务，writer 更新共享文件，inspector 提供检查工具。容器共享 Pod 的网络命名空间，所以 localhost 可以访问 server。每个容器仍然有各自的文件系统；通过共同挂载 emptyDir 才能共享 /data 文件。

本项目设置 shareProcessNamespace: true，inspector 可以查看其他容器的进程。阅读进程列表后，在《Pod项目实操学习手册》中执行终止 writer 的实验，比较 Pod UID、containerID 和 restartCount。容器重启时 Pod UID 保持一致；Pod 重建时 UID 改变。

7．理解探针、自愈和数据生命周期

机制 本项目的操作 应观察的结果
readinessProbe 删除 /data/ready 后恢复文件 Pod 暂停接收 Service 新请求，再恢复就绪
livenessProbe 删除 /data/live server 容器重新启动
Deployment 副本维护 删除一个 pod-web Pod ReplicaSet 创建替代 Pod
emptyDir 在 Pod 中创建标记后重建 Pod 新 Pod 使用新目录
PVC notebook 写入笔记后重建 Pod 笔记内容保留

startupProbe 在启动期间保护慢启动程序；readinessProbe 决定就绪状态；livenessProbe 失败达到阈值后触发容器重启。任务系统的 readiness 检查数据库连接，liveness 检查应用进程响应。数据库短时中断期间，应用暂时退出就绪状态，避免无效的重复重启。

练习删除前记录名称和 UID：

kubectl -n pod-lab get pods -l app=pod-web -o custom-columns=NAME:.metadata.name,UID:.metadata.uid,NODE:.spec.nodeName
kubectl -n pod-lab delete pod "$POD"
kubectl -n pod-lab rollout status deployment/pod-web --timeout=180s
kubectl -n pod-lab get pods -l app=pod-web -o wide

随后重新取得 POD 变量。自动重建能恢复声明的副本，应用的数据完整性需要存储、事务和备份配合。Local PV 绑定具体节点，NFS 数据可由多个节点访问；NFS 服务也运行在同一物理宿主机，仍然存在共同故障范围。

8．从 Pod 实验进入任务系统

任务系统包含 HTML/JavaScript 页面、FastAPI 后端和 PostgreSQL。用户登录后执行任务创建、读取、修改和删除，数据写入数据库 PVC。页面入口为 http://127.0.0.1:18083，可以通过下面命令建立转发：

kubectl -n interview-app get deployment,pod,service,pvc,hpa,pdb
kubectl -n interview-app port-forward service/tasks 18083:8080

使用私有凭据文件中的学习账号登录。创建一条自己能够辨认的任务，修改完成状态，刷新页面确认保存。打开后端日志，核对请求方法、路径、状态码及处理时间。删除一个应用 Pod 并等待副本恢复，再确认任务仍然存在。

正式验收使用源码 interview/verify-application.py 执行真实接口操作，包含认证与数据检查。执行脚本之前依照部署手册创建 Python 环境、设置 KUBECONFIG 并保持页面转发。

资源 requests 参与调度和 CPU HPA 利用率计算；limits 限制资源使用。CPU 达到限制可能出现节流，内存超过限制可能触发 OOM。当前 HPA 将副本数量控制在 2～4，CPU 目标值为 requests 的 50%。HPA 调整副本后，Argo CD 配置需要允许这个字段由 HPA 管理。

10．根据证据定位故障

先确认命名空间和对象，再查看状态、事件与日志：

kubectl -n interview-app get pods -o wide
kubectl -n interview-app get events --sort-by=.lastTimestamp
kubectl -n interview-app describe deployment tasks
kubectl -n interview-app get endpointslice
kubectl -n interview-app logs deployment/tasks --tail=50
现象 检查顺序 原因定位依据
Pending Pod 事件、requests、节点条件、PVC FailedScheduling 或卷绑定信息
ImagePullBackOff 镜像地址、仓库连接、CA、认证 拉取失败事件中的具体错误
CrashLoopBackOff previous 日志、退出原因、配置 进程退出码与最后一次状态

02：创建 Ubuntu 虚拟机

按《204节点RKE2集群搭建流程》的顺序完成宿主机依赖、Ubuntu 镜像校验、SSH 密钥、cloud-init 和四台虚拟机创建。源码中的 rke2-lab/network.xml、user-data、provision.sh 和四份 meta-data 是实际使用的配置。

在 94 宿主机验证：

virsh list --all
virsh net-dhcp-leases rke2-lab
virsh dominfo rke2-server-1
ssh -i /var/lib/rke2-lab/id_ed25519 ubuntu@192.168.204.11 hostname

需要理解的原理：libvirt 创建网桥和 NAT 网络；DHCP 根据固定 MAC 分配地址；cloud-init 首次启动时配置用户和 SSH 公钥；qcow2 提供虚拟磁盘文件。虚拟机的 4 GiB 内存是节点容量，Pod requests 和 limits 在这个容量范围内发挥作用。

03：安装 RKE2 并验证集群网络

同一版本的 RKE2 二进制、镜像包和校验文件必须配套使用。先安装 server，再让 agent 使用加入令牌访问 server 的 9345 端口。

在 server-1 执行：

sudo -i
export PATH=/var/lib/rancher/rke2/bin:$PATH
export KUBECONFIG=/etc/rancher/rke2/rke2.yaml
kubectl get --raw='/readyz?verbose'
kubectl get nodes -o wide
kubectl get pods -A

实验一：识别 Pod 和容器

kubectl -n pod-lab get deployment,pod,service
POD=$(kubectl -n pod-lab get pod -l app=pod-web -o jsonpath='{.items[0].metadata.name}')
kubectl -n pod-lab describe pod "$POD"
kubectl -n pod-lab get pod "$POD" -o jsonpath='{.metadata.uid}{"\n"}{.status.containerStatuses}{"\n"}'

观察 3/3 Running，表示三个普通容器均就绪。initContainer 单独显示在初始化状态中。Pod 有自己的 UID，三个容器分别有自己的 containerID 和 restartCount。

面试知识：Pod 是 Kubernetes 调度的基本单位。Deployment 通过 ReplicaSet 维持 Pod 数量。容器进程退出时 kubelet 根据重启策略处理；删除 Pod 后由上层控制器创建新的 Pod。

实验二：查看真实进程和 localhost 通信

kubectl -n pod-lab exec "$POD" -c inspector -- ps
kubectl -n pod-lab exec "$POD" -c inspector -- cat /data/writer.pid
kubectl -n pod-lab exec "$POD" -c inspector -- wget -qO- http://127.0.0.1:8080/status.json
kubectl -n pod-lab logs "$POD" -c writer --tail=10

本项目明确设置 shareProcessNamespace: true，因此 inspector 可以查看 writer 和 httpd 的进程。普通 Pod 默认不会在容器之间共享 PID 命名空间。相同 Pod 的容器共享网络命名空间，可以通过 localhost 通信。

面试知识：相同 Pod 的容器共享 IP 和端口空间，同时监听同一个地址、端口会产生冲突。进程共享需要显式配置。启用进程共享时，业务进程通常不会成为 PID 1；不要随意终止 PID 1。

实验三：终止 writer，观察容器重启

kubectl -n pod-lab get pod "$POD" -o jsonpath='{.metadata.uid}{"\n"}{.status.containerStatuses}{"\n"}'
kubectl -n pod-lab exec "$POD" -c inspector -- sh -ec 'kill -TERM "$(cat /data/writer.pid)"'
kubectl -n pod-lab get pod "$POD" -w
kubectl -n pod-lab logs "$POD" -c writer --previous --tail=10

writer 的 restartCount 增加，Pod UID 保持一致，server 容器继续运行。--previous 查看该容器上一次实例的日志。共享目录中的计数器在容器重启后保留。

实验四：readiness 和 liveness

kubectl -n pod-lab exec "$POD" -c inspector -- rm /data/ready
kubectl -n pod-lab get pods
kubectl -n pod-lab get endpointslice -l kubernetes.io/service-name=pod-web -o yaml
kubectl -n pod-lab exec client-allowed -- wget -qO- -T 5 http://pod-web:8080/status.json
kubectl -n pod-lab exec "$POD" -c inspector -- touch /data/ready
kubectl -n pod-lab wait --for=condition=Ready pod/"$POD" --timeout=60s
kubectl -n pod-lab exec "$POD" -c inspector -- rm /data/live
kubectl -n pod-lab get pod "$POD" -w

readiness 文件删除后，该 Pod 暂时停止接收 Service 新流量，server 的 restartCount 保持一致。恢复文件后重新进入就绪状态。liveness 文件删除后，server 容器被重启；启动脚本会重新创建该文件。

面试知识：startupProbe 保护慢启动；readinessProbe 控制是否接收流量；livenessProbe 控制是否重启容器。数据库短时不可达通常应影响应用 readiness。将数据库故障直接作为应用 liveness 失败条件，容易产生无效重启。

实验五：emptyDir 生命周期

kubectl -n pod-lab exec "$POD" -c inspector -- touch /data/ephemeral-marker
kubectl -n pod-lab delete pod "$POD"
kubectl -n pod-lab rollout status deployment/pod-web --timeout=180s
kubectl -n pod-lab get pods -l app=pod-web -o wide

重新取得新 Pod 名称，在 inspector 中检查 /data/ephemeral-marker。新 Pod 的 emptyDir 不包含原来的标记文件。initContainer 会为新 Pod 初始化新计数器。

面试知识：emptyDir 与 Pod 生命周期相关，容器重启不会清除它，Pod 删除后数据会丢失。emptyDir.medium: Memory 使用内存，其写入可能计入容器内存使用量。

实验六：PVC 和 StatefulSet

kubectl -n pod-lab exec notebook-0 -- sh -ec 'printf "完成 PVC 实验\n" > /data/notes.txt'
kubectl -n pod-lab get pvc
kubectl -n pod-lab delete pod notebook-0

kubectl -n pod-lab exec notebook-0 -- cat /data/notes.txt
kubectl get pv pod-lab-notebook -o yaml

Pod 名称仍为 notebook-0，UID 发生变化，笔记内容保留。该实验使用 worker-3 上的 Local PV，具有节点亲和性；节点不可用时不能自动迁移原有磁盘数据。回收策略为 Retain，删除 PVC 后需要管理员处理保留的数据和 PV 状态。

实验七：DNS、Service、网络策略

kubectl -n pod-lab exec client-allowed -- nslookup pod-web.pod-lab.svc.cluster.local
kubectl -n pod-lab exec client-allowed -- wget -qO- -T 5 http://pod-web:8080/status.json

实验八：RBAC

kubectl auth can-i list pods -n pod-lab --as=system:serviceaccount:pod-lab:learner
kubectl auth can-i delete pods -n pod-lab --as=system:serviceaccount:pod-lab:learner

实验九：三类常见故障

在源码目录执行：

kubectl apply -f faults/
kubectl -n pod-lab get pods -w
kubectl -n pod-lab logs fault-crash --previous
kubectl -n pod-lab describe pod fault-pending
kubectl -n pod-lab get pod fault-oom -o jsonpath='{.status.containerStatuses[0].state.terminated}{"\n"}'
kubectl -n pod-lab delete -f faults/
故障 真实触发条件 应检查的证据
CrashLoopBackOff 进程主动以退出码 7 结束 previous 日志、lastState、restartCount
Pending / Unschedulable nodeSelector 指定不存在的节点 PodScheduled 条件、FailedScheduling 事件
OOMKilled 16 MiB 内存限制下向 tmpfs 写入大量数据 terminated.reason、exitCode、内存限制

CrashLoopBackOff 表示重启退避状态，本身不说明程序失败原因。Pending 需要检查调度约束、资源、PVC 和污点。退出码 137 单独不足以证明 OOM，应同时检查 OOMKilled 状态和系统证据。

HPA、PDB 和错误发布

应用 HPA 根据 CPU 使用率扩缩容，目标为 requests 的 50%，最少两个、最多四个副本。计算目标依赖容器 CPU requests 和 Metrics Server。

PostgreSQL 逻辑备份与 Velero 恢复

backup-lab 命名空间的 CronJob 每六小时执行一次 pg_dump，将逻辑备份写入 database-dumps PVC。Velero 在备份生成半小时后，把该命名空间的资源和文件内容备份到 SeaweedFS S3，保留七天。

直接复制运行中的数据库数据目录，无法替代数据库一致性备份。本环境使用 pg_dump 生成可以交给 pg_restore 的逻辑备份文件。

kubectl -n backup-lab get cronjob,job,pvc,pod
kubectl -n velero get backupstoragelocation
kubectl -n velero get backup,restore,podvolumebackup,podvolumerestore
kubectl -n velero logs deployment/velero --tail=60

verify-backup.py 的验收过程：生成实际 dump → 执行 Velero 文件备份 → 恢复到 backup-restored → 比较 SHA256 → 确认源 PVC 与恢复 PVC 使用不同 PV → 创建新的 PostgreSQL 数据卷 → pg_restore → 查询原来的业务验收记录。

备份与恢复都必须达到 Completed，文件摘要一致且新数据库能够查询到记录，才能确认这一恢复链路有效。
